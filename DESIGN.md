## Brand
- Personality: reliable logistics cabinet, clear, modern, confident, not playful.
- Trust signals: agent branding, client code visibility, warehouse copy actions, status clarity.
- Avoid: dense grids, tiny primary actions, low-contrast date/status metadata, decorative UI that hides operational actions.

## Product goals
- Goals: make the home screen a quick operational dashboard; help users add and manage tracks/assemblies, copy warehouse data, contact their agent company, browse all no-code goods with warehouse photo evidence, browse photo reports, see latest changes in seconds, and let an SP organizer run the full purchase-to-delivery workflow without leaving 2A.
- Non-goals: removing existing content, silently changing existing money/data semantics, replacing established logistics screens with duplicate SP screens, or creating a separate visual system for new features.
- Success signals: primary action is obvious, scan path is top-to-bottom, digest tabs are easy to tap, cards feel consistent and premium.

## Personas and jobs
- Primary personas: clients tracking parcels, invoices, assemblies, photo reports, and warehouse delivery details.
- User jobs: check current state, open profile from the identity block, add track numbers, filter/search/sort tracks and assemblies, copy warehouse address/phone, contact the current agent by phone, email, messenger, social network, or website, browse warehouse photo/video reports by date, find a track that is not yet linked to the client code, open latest item details.
- Key contexts of use: mobile-first, one-handed use, intermittent connectivity, returning users who need fast status checks.

## Information architecture
- Primary navigation: mobile and tablet portrait use bottom navigation; iPad landscape, macOS, and desktop web use a left side rail plus the same floating top menu. The `Ещё` entry opens a premium quick-action sheet, not a dense full-screen menu.
- Core routes/screens: home, tracks, invoices, photos, profile/more, referral program, partner program, and `sp-finance` with purchases, customers, products, analytics, and purchase detail.
- Content hierarchy: floating shell navigation -> greeting/client identity -> primary action -> current client CNY/RUB rate with its publication date -> summary metrics -> optional promo/warehouse -> agent contacts -> secondary no-code goods entry -> latest updates digest; the contact card follows the warehouse block and exposes only published fields from the same agent profile payload; the no-code catalog opens with all agent-scoped NOCODE goods, optional server search, server pagination, and warehouse photo evidence inside each card; tracks screen uses brand archive header -> view mode control -> compact action controls -> virtualized track/assembly list -> load/end state; photos screen uses brand archive header -> date groups -> virtualized photo grid -> load/end state; invoices screen uses brand archive header -> inline search/filter controls -> invoice cards focused on invoice number and USD amount -> detail sheet with summary, cargo, calculation, bonus, and media sections; client-code switcher adds per-code operational counters for quick account choice; More sheet starts with two-column service shortcuts (`Чат по оплатам`, `Чат поддержки`, then available `Самовыкуп` and `Гараж`) and continues with one ordered single-column service list. Manual update checking appears only in direct-distribution Android builds and is absent from RuStore and non-Android builds.

## Design principles
- Principle 1: operational clarity beats decoration; every prominent block should answer “what can I do now?”.
- Principle 2: one visual system per screen; cards, radii, shadows, and pills should feel related.
- Principle 3: external product references may define interaction completeness and information architecture, but implementation must use native 2A components, branding, terminology, accessibility, and responsive behavior.
- Principle 4: visual improvement must not change existing business meaning or saved data; old and new purchases must coexist on the same screens.
- Tradeoffs: preserve existing backend/provider behavior and introduce new surfaces incrementally, even when a clean rewrite would be shorter.

## Visual language
- Color: use dynamic agent brand colors for hero, primary action, selected states, and accents; neutral white cards on `#F2F2F7` background.
- Typography: Gilroy, bold for dashboard numbers and card titles; small semibold metadata for dates and weekly deltas.
- Spacing/layout rhythm: 8-14 px internal rhythm for dashboard density, 18-24 px radii on cards, larger tap targets than the old 24-30 px controls.
- Shape/radius/elevation: soft premium cards, subtle shadows, pill metadata/statuses, floating glass navigation with 18-24 px radii. Every mobile modal sheet uses one 30 px radius on both top corners (and square bottom corners); feature sheets must open through the shared modal route so transparent or legacy content cannot lose that outer shape.
- Motion: light staggered reveal for dashboard blocks, subtle loop on the hero/primary CTA, softly animated hero backdrop circles clipped from card edges, animated active bottom-nav pill, `AnimatedSwitcher` for digest tab content; no heavy or blocking animations on home.
- Imagery/iconography: Material/Cupertino operational icons; icons support scanning but do not replace labels.

## Accessibility
- Target standard: mobile readable contrast and 44 px-ish tap targets for core actions.
- Keyboard/focus behavior: keep current Flutter navigation behavior; no custom keyboard traps.
- Contrast/readability: avoid pale metadata on white; statuses use tinted pills with readable text.
- Screen-reader semantics: labels remain text-first; icons are supplemental.
- Reduced motion and sensory considerations: motion is short and non-essential.

## Responsive behavior
- Supported breakpoints/devices:
  - Mobile: `< 600px`, touch-first, one-column content, bottom navigation.
  - Tablet portrait: `600–1023px`, centered content up to ~760px, bottom navigation constrained to a comfortable width.
  - iPad landscape / desktop: `>= 1024px` or `>= 840px` when landscape, left side rail replaces bottom navigation, bottom obstruction is removed, content is centered.
  - Wide desktop/web/Mac: `>= 1440px`, content max width increases but operational cards never stretch edge-to-edge.
- Layout adaptations: shell pages are constrained through `AppLayout.constrainNavigationContent`; root routes through `AppScaffold` are constrained through `AppLayout.constrainContent`; stat grids/cards should use 2–4 columns only when the local content width supports it; digest tabs horizontally scroll instead of squeezing text; photo reports grid uses fewer larger columns on mobile and more columns on wider web; all modal sheets are constrained to tablet/desktop modal widths instead of spanning the whole monitor. Every shared modal with `useSafeArea` keeps interactive content above Android gesture and three-button system navigation insets; nested SafeArea widgets receive the consumed inset and must not add it twice. Assembly scan detail stays within an explicit 1120px maximum even beside desktop navigation; at desktop width its video and scanned-track evidence use two balanced columns, while mobile remains one column.
- Touch/hover differences: touch actions remain primary; desktop may show tooltips and hover/InkWell states but must not rely on hover-only controls. Side navigation labels are always visible enough to identify sections.

## Content voice
- Tone: concise, useful, operational.
- Terminology: use existing logistics terms: треки, сборки, счета, фото, склад, код клиента.
- Microcopy rules: prefer action verbs; avoid long explanations inside compact controls.

## Implementation constraints
- Framework/styling system: Flutter/Dart in `2a-user`; dynamic brand colors via theme/context.
- Design-token constraints: no new global design system unless reused elsewhere.
- Performance constraints: keep home digest lightweight; preserve `AppCachedMediaImage` for photos and keep photo archive on `CustomScrollView`/`SliverGrid` virtualization.
- Compatibility constraints: do not touch generated Dart files; preserve web/mobile behavior.
- Video playback constraints: use authenticated, short-lived, range-capable playback URLs; preserve marker seek on mobile and web and do not expose permanent storage object URLs.
- SP compatibility constraints: only additive API/model evolution; new fields are optional; old DTOs and old purchases remain renderable; new screens must support capability-off, mixed legacy/new data, and no automatic recalculation of historical money.
- Test/screenshot expectations: run `dart format`, `flutter analyze`, and visual smoke through Flutter web/mobile when possible.
- SP test/screenshot expectations: add regression fixtures before business-logic edits; validate 320/390 px, tablet, desktop web, and macOS; visually compare against existing 2A surfaces, not against copied foreign assets.
