# Safe Refactoring Protocol

## Non-negotiable sequence

Для ЛЮБОГО рефакторинга выполняй шаги по порядку. Пропустить шаг = сломать прод.

### Шаг 1 — Impact analysis

**Перед любым редактированием** вызови:

```
gitnexus_impact({target: "<имя символа>", direction: "upstream"})
```

Это покажет всех, кто зависит от символа. Если прямых зависимостей много (>10) или risk level HIGH/CRITICAL — остановись и доложи пользователю.

Для classes/types дополнительно вызови `gitnexus_impact` с `direction: "downstream"`, чтобы увидеть, что символ использует.

### Шаг 2 — План

Сформулируй план рефакторинга явно:

```markdown
### План рефакторинга `OldClassName`

**Цель:** ...

**Изменения:**
1. Создать новый класс `NewClassName` в `path/to/new_file.dart`
2. Перенести методы: `method1()`, `method2()`
3. Обновить все call-sites (всего N штук, список ниже)
4. Удалить старый класс

**Call sites для обновления:**
- `path/a.dart:42` — `OldClassName()` → `NewClassName()`
- ...

**Риски:**
- Изменение публичного API → нужно обновить тесты
- ...
```

Дождись одобрения пользователя.

### Шаг 3 — Реализация порциями

Не делай всё сразу. Разбей на commits:

1. Создать новое (ещё не удаляя старое)
2. Переключить один call-site, проверить тесты
3. Если ок — переключить остальные
4. Удалить старое

### Шаг 4 — Rename с помощью графа

Для переименования **никогда не используй find-and-replace**. Используй `gitnexus_rename` (если доступен) или обновляй call-sites по одному, используя `gitnexus_context` для каждого.

Find-and-replace ломает:
- Вхождения в строках (docs, tests)
- Похожие имена (например, `User` и `UserProfile` при замене `User` → `Customer`)
- Импорты в не-индексированных файлах

### Шаг 5 — Detect changes перед коммитом

```
crg_detect_changes({scope: "working"})
```

Должен показать:
- Только ожидаемые файлы
- Затронутые символы — только те, что ты планировал
- Тесты обновлены (если ломал API)

Если видишь неожиданные изменения — не коммить, разберись.

## Red flags — немедленно останови рефакторинг

1. `gitnexus_impact` показывает >20 прямых зависимостей → разбей на меньшие шаги
2. Risk level = CRITICAL → уточни у пользователя, нужен ли вообще этот рефакторинг
3. Символ используется в тестах, но они не обновлены → обнови тесты ПЕРЕД сменой API
4. Генерируемые файлы (*.g.dart) ссылаются на символ → нужна регенерация

## Шаблон сообщения пользователю при HIGH risk

```
⚠️ Impact analysis показал HIGH risk для этого рефакторинга:

- Прямые зависимости: N
- Execution flows, затронутые: M
- Risk level: HIGH

Список зависимостей:
[...]

Продолжить? Варианты:
A. Да, делай
B. Разбей на меньшие шаги — покажи план
C. Отмени, рефакторинг не нужен
```
